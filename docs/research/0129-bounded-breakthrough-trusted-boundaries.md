## 3. Confirm the trusted boundary before execution

Before launching any breakthrough trial, write a concrete run contract:

1. **Question and level.** State the finite input family, the requested
   conclusion, the current computational or linguistic level, and the
   counterexample or witness that would resolve this particular question.
2. **Imported knowledge.** Identify each source domain, the exact result or
   assumption being used, its scope and side conditions, and the evidence
   already available. Keep conjectures and observations explicitly labelled.
3. **Interface.** Specify what is translated into the target problem, which
   equality or equivalence is required, which distinctions are retained or
   forgotten, and what justifies that translation. Similar names or formulas
   do not supply this justification.
4. **Protected obligations.** List the source-domain facts and checks that
   must survive. An improved score, shorter program, or promising candidate
   cannot compensate for losing one of these obligations.
5. **Acceptance and verification.** Fix the candidate family, checker,
   negative controls, success condition, and unresolved outcomes before
   searching. Proposal generation cannot supply its own unchecked authority.
6. **Resources and exit.** Set numeric bounds for search work, elapsed time,
   memory, retained artifact size, and continuation count as applicable.
   Include checking and checkpoint costs, with enough reserve to stop and
   retain the result. Record how each bound is enforced.

If a necessary interface justification or enforceable resource bound is
missing, retain it as a preflight obstruction and do not launch that trial.
Clarifying such an obstruction is useful work in its own right.

External mathematical evidence remains external evidence. Native semantic
identities and transformations continue to require the existing Rust

## 4. Finite attempts and explicit continuation

Each run ends at a checked witness, a checked counterexample, a completed
declared finite search, a resource limit, an invalidated assumption, a checker
failure, or an explicit stop request. Resource exhaustion reports `Unknown`
with its stopping reason. Completing one declared family can establish only
a separately checked result about that family, not unrestricted nonexistence.

Budget accounting covers retries, subsearches, verification, and any nested
continuation. There is no automatic budget reset, enlargement of the candidate
family, or indefinite outer loop after an unsuccessful attempt. A step that
cannot be cooperatively bounded needs a supervisor with a timeout or another
declared enforcement mechanism before launch.

On exit, preserve the question and assumption versions, candidate order,
actual costs, checked evidence, failures, residuals, and continuation cursor.
Never promote a partially checked candidate. If checkpointing fails, report
that failure and do not claim a resumable record exists.

A later continuation needs an explicit revised run contract, a rechecked
boundary, a finite budget, and a reason to expect useful new evidence. It can
proceed within the authorization already given; this rule does not require
repeated permission for unchanged, authorized work. It does require stopping
when the authorized scope or its trusted boundary is no longer established.

An energy or gradient score may order admissible proposals. It does not
override admission, define physical energy, guarantee a shortest route, or
guarantee termination. Potentially continuing research is a sequence of
finite accountable attempts.

These are operating requirements for future trials. This documentation change
does not implement a supervisor, scheduler, or native `breakthrough` command.
