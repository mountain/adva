# Research 0155：密码学封存、双语言校准与 Adva 的信任边界

日期：2026-09-06。状态：`proposed-document`，文档登记，不是执行报告。
来源：Mingli Yuan 关于“目前体系内更强、Python 和 Rust 都支持的加密算法”
的提问，以及将详细说明纳入知识库的要求。

本文区分已检查的仓库事实、外部算法资料与尚未实现的设计建议。
登记本文不安装密码库、不生成密钥、不签署现有义务、不运行密码学实验，
也不批准一个新的原生语义阶段。当前几何义务继续为 `Open`，原生 `Seal`
继续为 `NotIssued`。

## 1. 结论与适用问题

当前要问的不是笼统的“哪个算法更强”，而是希望增强哪一种保证：

| 问题 | 合适的机制 | 不能由它推出的结论 |
| --- | --- | --- |
| 文件是否仍与可信检查点一致？ | 已有 SHA-256／BLAKE3 摘要及独立保存的基准 | 谁批准了文件、命题是否为真 |
| 谁批准了这一版本的义务记录？ | 数字签名、可信公钥绑定和授权策略 | 签名者判断正确、义务已经解除 |
| 数据不应被未授权方读到？ | 认证加密及密钥管理 | 数学证明、公开可验证的作者身份 |
| Python 与 Rust 是否执行同一规定计算？ | 固定向量、交叉检查和拒绝控制 | 普遍正确性、密码安全证明、实现完全独立 |
| 一个 Adva 变换是否有权被接受？ | 对应的 Rust 原生检查及证书 | 不能由外部签名或摘要替代 |

针对目前的公开知识库和生长义务，本文建议优先研究
**保留摘要，加上 Ed25519 签名及独立的信任策略**。
若另有保密要求，再评估 AES-256-GCM 或 ChaCha20-Poly1305。
这是根据当前需求作出的工程选择，不是三个算法的安全强弱排名。

## 2. 本地基线：已有的是什么

本次以源码和当前 `.venv` 的包元数据为依据，未把网络文档当作安装结果：

- [Cargo.toml](../../Cargo.toml) 声明 `blake3`；
  [witness.rs](../../crates/adva-witness/src/witness.rs) 中的
  `ArtifactKeyV0::digest` 对研究 witness 的序列化内容做 BLAKE3 摘要。
  该键是非语义的内容寻址坐标，不是 `SourceId` 或 `OccurrenceId`。
- [math_catalog.py](../../python/adva/math_catalog.py) 使用标准库
  `hashlib.sha256` 检查目录引用和固定的生长义务。
- [pyproject.toml](../../pyproject.toml) 没有声明本方案的签名或认证加密依赖；
  当前 `.venv` 没有安装 `cryptography`、`PyNaCl` 或 Python `blake3`。
  Python 没装 `blake3` 不影响 Rust 已有的 BLAKE3 用途。
- [生长义务](../../adva-library/math/constraints/growth-obligation-v0000.json)
  的固定 SHA-256 是
  `8f3f457b4991752ec1284968c8e36feffb0ce59aa96d6f63993c3f98396a2c03`。
  [documentary seal](../../adva-library/math/constraints/growth-obligation-seal-v0000.json)
  记录的是 `RecordedOpen`，没有数字签名，也没有原生 Seal。
- `adva.py math-check` 只检查声明的目录结构与字节引用；其报告继续明确
  `proofs_rechecked: false`、`recorded_claims_authenticated: false` 和
  `native_admission: not-granted`。

固定摘要可以发现相对基准的变化；若攻击者能同时替换内容、检查器和基准，
摘要本身不能恢复一个独立的信任来源。换一个更长的摘要不解决这个问题。

## 3. Python 与 Rust 的共同支持

下面是截至上述日期核对的公开接口，不是已锁定的构建配置。
`stable`／`latest` 文档会更新；实施前必须另行锁定包版本、特性、后端、
工具链和依赖锁文件，并检查目标平台支持及当时的安全公告。

| 用途 | 算法／配置 | Python 接口 | Rust 接口 |
| --- | --- | --- | --- |
| 认证加密 | AES-256-GCM | `cryptography.hazmat.primitives.ciphers.aead.AESGCM`，32 字节密钥 | `aes-gcm::Aes256Gcm` |
| 认证加密 | IETF ChaCha20-Poly1305 | `cryptography.hazmat.primitives.ciphers.aead.ChaCha20Poly1305` | `chacha20poly1305::ChaCha20Poly1305` |
| 数字签名 | 普通 Ed25519 | `cryptography.hazmat.primitives.asymmetric.ed25519` | `ed25519-dalek` 的签名／验签接口 |

接口来源：[Python AEAD](https://cryptography.io/en/stable/hazmat/primitives/aead/)、
[Python Ed25519](https://cryptography.io/en/stable/hazmat/primitives/asymmetric/ed25519/)、
[Rust AES-GCM](https://docs.rs/aes-gcm/latest/aes_gcm/)、
[Rust ChaCha20-Poly1305](https://docs.rs/chacha20poly1305/latest/chacha20poly1305/)、
[Rust Ed25519](https://docs.rs/ed25519-dalek/latest/ed25519_dalek/)。

### 3.1 加密配置与误用边界

AES-GCM 和 ChaCha20-Poly1305 都是 AEAD：保护密文的机密性与完整性，
并认证不加密的附加数据 AAD。拟议互操作配置固定为 12 字节 nonce、
16 字节认证标签；AES 固定选 256 位密钥，不靠模糊的 `AES` 名称协商。
同一密钥下不能重用 nonce。参见
[Python AEAD 参数与警告](https://cryptography.io/en/stable/hazmat/primitives/aead/)、
[NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) 和
[RFC 8439](https://www.rfc-editor.org/rfc/rfc8439)。

本项目的设计约束是：正式用途的 nonce 分配必须考虑崩溃恢复、并发写入和
密钥轮换，不能只写一句“每次随机生成”就认为生命周期已解决。
只对公开、弃用的测试密钥重放固定向量；不得将这种重放习惯用于真实数据。
加密失败或认证失败时不向调用者释放未经认证的明文。

本说明不选择 XChaCha、缩减轮数变体、裸 ChaCha 流加密或另造加密组合。
Rust 提供其他变体不等于它们与这里的 Python 接口是同一种协议。
不通过叠加多种算法来宣称“多重加密一定更强”。

### 3.2 签名配置与误用边界

拟议基线为普通 Ed25519：公钥编码 32 字节，签名 64 字节；
这些长度不是把整个系统安全性换算成“256 位”的依据。
普通 Ed25519、Ed25519ph 和 Ed25519ctx 必须区分；对一个摘要调用普通
Ed25519 签名，不等于调用 Ed25519ph。依据
[RFC 8032 第 5、7、8 节](https://www.rfc-editor.org/rfc/rfc8032)。

Python 的原始私钥输入与 Rust 的私钥／密钥对序列化不能凭名称互换。
未来适配器需明确是种子、原始公钥还是 PKCS#8，拒绝不符格式；
默认只交换公钥、消息和签名，不跨进程传递生产私钥。
参见 [Python 密钥接口](https://cryptography.io/en/stable/hazmat/primitives/asymmetric/ed25519/)
与 [Rust 序列化接口](https://docs.rs/ed25519-dalek/latest/ed25519_dalek/)。

本文不建立长期抗量子保证、不完成算法迁移策略，也不声称选用这些算法
就获得某种合规认证。这些需求需要独立的威胁模型与审核。

## 4. 三种 seal 不能合并

| 名称 | 实际判断 | 当前状态 |
| --- | --- | --- |
| documentary `seal` | 指定义务字节与固定检查点相符，保留 Open | 已有目录检查 |
| cryptographic signature | 指定公钥下的消息／签名关系成立；授权另判 | 本文方案，未实现 |
| Rust `WitnessProofV0::Seal` | 已形成 witness 的乘法残余闭合，保留其其他义务 | 已有研究 witness 机制，不适用于任意 JSON 义务 |

Rust 的 `Seal { body }` 先要求 body 已形成，再检查乘法残余是否为单位。
它没有把任意自然语言、JSON 声明或外部定理自动变成已证事实。
具体非零条件仍须按原有方法检查，见
[witness.rs](../../crates/adva-witness/src/witness.rs) 及
[Research 0154](0154-math-catalog-and-task-loop-boundary.md)。

因此，给“Pascal 导入义务尚未完成”签名，至多认证了这份未完成记录的来源。
它不能生成 Pascal 的 Rust 导入证书，不能解除几何生长义务，也不能成为
新的推导父节点。签名为真与被签命题为真是不同判断。

## 5. 自我生长程序的威胁模型

下表是拟议防护需求，不是已经部署的安全保证：

| 可能发生的行为 | 需要的防护 | 单靠摘要／签名的不足 |
| --- | --- | --- |
| 修改材料但保留旧引用 | 从可信起点复核字节摘要 | 基准一并被换后不能自救 |
| 修改义务并重新计算所有摘要 | 独立授权签名及受保护的检查器／公钥 | 放在同一可写目录的公钥可一起被替换 |
| 搜索程序取得签名密钥或任意签名接口 | 独立审批与用途受限的签名主体 | “私钥不在仓库”仍可能留下无限制签名服务 |
| 重放旧的合法签名版本 | 可信的最新版本状态及回滚策略 | 有效签名不代表版本最新 |
| 同一父版本产生两个合法分支 | 独立的分支审批、审计或一致性机制 | 前驱摘要链不自动防分叉、不建立共识 |
| 正确签署了一个错误数学声明 | 原来的证明检查与语义边界 | 签名不会纠正签名者的错误 |
| 检查器或运行主机被控制 | 受保护的部署与执行边界 | 库内一个检查命令不是 OS 安全沙箱 |

核心约束是：**候选生成器不能决定自己将受哪套检查，也不能给自己批准
一套更宽松的义务。** 密钥保管、受信公钥、批准权限、版本状态和检查器
发布渠道必须有至少一个不受候选生成器控制的外部信任起点。

这不要求把所有知识加密。公开义务通常更需要可审查与可追溯；
把它加密到检查者无法读取，会引入新的可用性和密钥分发问题。

## 6. 拟议签署对象：先固定“批准了什么”

未来应评审一个独立、版本化的签名封装，不能往现有严格 v0 JSON 中随意
增加字段，也不能重写现有义务来适配签名。至少要明确覆盖以下信息：

- 协议名称、封装版本与用途域，例如“生长义务批准”，避免签名跨用途复用；
- 所属项目、条目 home、义务版本、目录政策版本及其精确字节引用；
- 被批准材料的摘要算法、摘要及明确范围；没有列入的文件不获得批准；
- 本次批准的动作，例如“保留 Open 记录”，不能默认为“解除义务”；
- 前驱记录、序号与分支信息，以及由外部策略判断的新鲜性；
- 签名算法、公钥标识和适用的授权策略版本。

这里列的是协议需求，不是注册了一个可执行 schema。公钥标识只是查找
坐标，不能代替从受信渠道得到的公钥。签名算法也不得由不可信输入选择
后任意降级或回退到“只检查摘要”。

### 6.1 字节与 JSON 边界

签名对象必须是明确定义的字节。不能假定 Python 与 Rust 重新序列化同一
JSON 值后必然得到相同字节，也不能把签名成功后的另一份重读内容作为输入。
需评审选择“保留并签署精确 payload 字节”，或一种明确、版本化的规范编码。
字符串编码、数字格式、字段顺序、重复键和 Unicode 处理都必须固定。

验签、结构检查和后续引用验证应绑定同一个不可变输入快照；
禁止验签后重新读取可变文件而不再检查。签名、摘要和结构检查的具体执行
顺序须考虑资源限制，但验签结果不能授权跳过结构、范围或原生检查。

### 6.2 密钥生命周期

生产私钥不进入 Git、普通日志、测试夹具、命令行参数或搜索候选可读空间。
应另行确定保管者、生成方式、备份恢复、用途限制、轮换、撤销和泄露响应。
同一签名者的多把密钥不等于多个独立批准者；多人签署也不自动满足三计算。
本次文档登记没有替用户选择保管者，没有建立实际信任关系。

## 7. 与三计算、verifier search 的关系

应分开记录至少三个不同谓词：

1. `SignatureValid`：精确消息与指定公钥下的签名关系成立。
2. `AuthorizedForPurpose`：该公钥根据独立策略有权批准此用途和版本。
3. `SemanticallyChecked`：相应命题或程序通过其实际语义检查。

以上名称仅为本文说明标签，不是新的 Rust 类型或已有报告状态。
前两个成立不推出第三个；第三个成立也不能推出作者身份或当前授权。

Python 与 Rust 都验签成功，可以提供跨实现一致性证据；
它们若共享同一后端或同一输入误解，也可能一起犯错。
规范测试向量是外部参考，不是一个会执行判断的第三 verifier。

现有 Rust／Lean／Metamath 校准针对限定算术命题，并没有因此获得
Ed25519、AES 或 ChaCha 的完整规范与证明。不能把“Rust 密码库 + Python
密码库 + Adva 调度器”重新命名为已经满足三计算约束。
未来如要作形式校准，必须说明各检查器实际判定的命题、信任基础、
输入翻译和残余；一个依赖 Lean／Metamath 的密码学证明目前并未提供。

## 8. 密码算法如何成为有限计算任务

密码算法适合提供明确的字节级输入与可比较输出，但这里的任务是验证
实现和协议边界，不是搜索真实密钥、破解密文或自动发明生产密码算法。

拟议的外围 loop 是：固定配置与样例 → 两侧计算 → 对照已知答案及彼此输出
→ 检查拒绝行为 → 保留证据与残余 → 在剩余预算内处理下一个样例或停止。
它不是 Adva 原生递归、反馈闭合或稳定 `loop` 算子。

### 8.1 样例与判定

| 任务 | 必须比较的对象 | 不能用作唯一验收依据的替代物 |
| --- | --- | --- |
| AEAD 已知答案 | 固定 key、nonce、AAD、明文对应的密文和完整 tag | 自己加密后自己解密成功 |
| AEAD 互操作 | Python 加密／Rust 解密及反方向，编码精确相同 | 只比较两侧是否都“无异常” |
| Ed25519 已知答案 | 固定公开测试种子、消息、公钥及签名 | 两个实现都接受各自产生的签名 |
| Ed25519 互操作 | 双向签名验签及固定消息字节 | 只比较签名长度 |
| 拒绝控制 | 错误消息、key、AAD、nonce、tag、签名或不合法编码 | 将异常吞掉后视作成功 |
| 策略控制 | 未授权 key、错误 home／版本／用途、旧版本与分支冲突 | 密码验签成功即准入 |

优先从 [RFC 8032 第 7 节](https://www.rfc-editor.org/rfc/rfc8032)、
[RFC 8439 第 2.8.2 节及附录](https://www.rfc-editor.org/rfc/rfc8439) 和
[NIST GCM 测试向量入口](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program/cavp-testing-block-cipher-modes)
选择有限样例，并在执行前保存来源、向量编号、原始字节摘要与选择清单。
当前仅核对了资料入口，未下载固定向量集，未记录任何通过结果。
NIST 也明确区分使用公开向量作非正式检查与正式 CAVP 验证。

空消息、非 ASCII 字节、分块边界、最大声明长度、截断输入和编码错误
应进入明确的有限测试集。畸形 Ed25519 编码的接受规则必须固定；
若两个实现对此分歧，保留差异并停止相关准入，不能投票选一个“正确结果”。
nonce 重用的拒绝属于外围策略检查，不能假定底层 AEAD 库会替用户记住
此前使用过的所有 nonce。

### 8.2 可审查的有限预算模板

以下数字只是首次工具校准的候选上限，不是已获执行授权的 run contract：

| 资源 | 候选上限 | 实施时必须具备的约束 |
| --- | ---: | --- |
| 完整测试记录，包含正例和负例 | 64 | 执行前固定清单，新增变体也计数 |
| 单条消息／AAD | 4 KiB／1 KiB | 调用前检查字节长度 |
| 密码后端操作总数 | 1,024 | 签名、验签、加解密及失败调用共享计数 |
| 子进程启动总数 | 4 | 使用已构建的声明后端，所有启动计数 |
| 总墙钟／总 CPU | 60 秒／30 秒 | 从预检至最终记录，外部监督而非仅循环内检查 |
| 进程树总内存 | 256 MiB | 聚合资源限制，不能只限制单个子进程 |
| 输入累计读取／输出累计写入 | 16 MiB／16 MiB | 含 pin 扫描、日志和最后检查点的计量 |
| 重试／嵌套搜索／自动续跑 | 0／0／0 | 失败保留；不重置 fuel |
| 生产密钥访问／原生准入 | 0／0 | 仅公开测试材料，禁止自动签署真实义务 |

执行前还缺：具体向量 pins、两侧版本和二进制身份、已审核的适配器、
接受规则、上述限制的实际执行机制，以及退出记录所需预留。
任一项缺失即 `NotRun`。构建与安装不藏在这个运行预算之外自动进行；
若另行批准准备阶段，也必须单列有限合同与成本。

建议报告区分：尚未启动 `NotRun`；某个已检查控制按预期拒绝；
实现差异或检查器错误；运行耗尽资源 `Unknown`；以及“声明的有限样例全部
符合预期”。这些是待定义的报告语义，不是已有 CLI 返回值。
耗尽预算不代表算法不安全，样例全过也不代表算法普遍安全。
失败、未运行项、候选顺序、实际用量和残余均须保留，不自动进入下一轮。
这遵循 [Research 0129](0129-bounded-breakthrough-trusted-boundaries.md)。

## 9. search／梯度能改变什么

## 11. 进入实现前的门槛

本文不改变 [研究工程议程](../RESEARCH_ENGINEERING_AGENDA.md) 的依赖顺序。
可以区分三个尚待批准的范围，不能因前一层成功而自动晋升：

1. **外围互操作校准**：固定公开向量和后端，落实有限合同，只产出外部证据。
2. **实际封存认证**：另行确认受信公钥、批准主体、协议编码、回滚和撤销策略；
   使用独立版本的封装，不改写历史 checkpoint，也不把 Open 改成已解除。
3. **原生密码学计算或证明**：先满足精确整数／有限域／位运算、有限数据与
   控制、序列化和 certificate 的语义前提，再单独评审 Rust 操作族与 IR。

研究代码能调用 host 大整数，不代表 PSC0 已具备同样的原生表示。
`f64` 不能充当密码学精确计算的语义 oracle；Python 不能暗中补齐缺失语义。
即使由 Rust 调用一个密码 crate，它也不会自动成为 Adva 原生证明检查器。

外围入口继续尊重 `python/adva/adva.py`。若未来增加命令，应在那里明确
暴露范围和结果，但本文没有新增 `crypto-check`、`sign`、`encrypt` 或 loop
命令，也没有把这些候选命令作为现在能运行的示例。
