## 1. 结论与适用问题

防篡改检测的核心是**哈希链 + 独立分发的锚点**，零知识证明本身不负责
发现篡改。ZKP 在本方案中只承担两个哈希链给不了的能力：

1. **披露边界**：证明“序列位置 i 存在一个通过检查器 P 的命题”，而不泄露
   命题内容，直到约定的披露时刻。这是
   `pascal-task.adva` 中 `secret: payload_included: false`、
   “不因不披露而推断知识或真值”纪律的密码学实现。
2. **常数级审计**：用递归组合证明把“整条链均合法”压缩为一次常数代价的
   验证（可选加速层，默认关闭）。

| 问题 | 合适的机制 | 不能由它推出的结论 |
| --- | --- | --- |
| 某条记录是否被改过？ | SHA-256 哈希链 + Merkle 检查点 + 锚点 | 改动者是谁、命题是否为真 |
| 谁发布了这批记录/锚点？ | Ed25519 签名 + 独立授权策略 | 签名者判断正确、内容语义正确 |
| 给维护者签发签名密钥与用途授权？ | key-issue 工具 + 独立授权策略 | 数学语义准入、命题为真 |
| “存在通过检查器 P 的隐藏候选” | 承诺 + NIZK/SNARK | 候选内容、作者身份、P 的电路忠实于原检查器 |
| 整条长链是否全局一致？ | 全量重放（L1）或 IVC 递归证明（L2d） | IVC 的密码假设成立、电路无漏洞 |
| 一个命题是否有权被接受？ | 对应的 Rust 原生检查与证书 | 不能由摘要、签名或 SNARK 替代 |

三类凭据的分工沿用 Research 0155 的分离原则：**签名管“谁”、摘要链管
“改没改”、ZKP 管“谓词是否成立”**。三者任一成立都不推出其余两者。

## 2. 对象与威胁模型

### 2.1 被保护对象

“有限算术命题的证明发现序列”在本文中指：按时间顺序追加的、每项含命题、
环境、检查器、判定与残余的有限记录链。现有材料已具备这一形态：

- `knowledge-boundary/` 的 k27 判题回执（Q 上精确有理数，residual 保留）；
- `stability/epoch-0000/0001` 的知识纪元（父链重放）；
- `exploration/0151/` 的提案日志（含拒绝与 Unknown）；
- `prime-universe/` 的有限请求与判定；
- `pascal-witness.adva` 的 27 项外部算术检查与控制组。

本方案不重新解释这些文件的语义，只在其外围加一层可分离验证的完整性骨架。

### 2.2 三包分离假设

`math/` 目录已把算术、几何、逻辑分为三个主题（ADR 0042），每条目唯一
home。假设未来三者成为独立的包（乃至独立仓库），彼此通过
`(package, seq, digest)` 引用。方案必须满足：

- 任一包的任何维护者凭本地文件 + 一份锚点副本即可完成检查；
- 检查时刻不需要第三方服务器；
- 几何与逻辑的序列损坏不能使算术序列的检查失效，反之亦然。

### 2.3 篡改的含义

改单字节、删记录、插入伪造、重排序、整链重写（连带重算哈希）、跨包引用
指向被改记录、替换锚点。最后一项是根本信任边界，见 5.4。

## 3. 总体架构

四层，任何一层失效时下层仍完整工作：

| 层 | 职责 | 失效时 |
| --- | --- | --- |
| L0 原生规则 | 记录格式与转移规则 R，由 Rust 判定语义 | 方案不改变它 |
| L1 篡改可见脊梁 | 规范化字节、哈希链、Merkle 检查点、锚点 | —（骨架，必须） |
| L2 零知识层 | 披露边界、谓词 SNARK、跨包包含证明、可选 IVC | 退回 L1：只失去隐私与常数级审计 |
| L3 检查协议与凭据工具 | `tamper-check`、`key-issue`、`verify` 三个 CLI 与报告 | 人工按 L1 规则重放 |

## 4. L0：记录格式与转移规则

每条发现记录规范化后至少包含：

| 字段 | 说明 |
| --- | --- |
| `seq` / `package` | 包内单调序号；`arithmetic` / `geometry` / `logic` |
| `schema` / `version` | 记录模式版本 |
| `proposition` | 沿用现有表达式语法：整数、变量、+、−、*、括号；无浮点、无除法 |
| `environment` | 绑定与前提 |
| `checker` | 检查器 id + 版本 + 判据 |
| `verdict` / `residual` | Verified / Rejected / Unknown，附残余 |
| `cites_same_home` | 同包父引用 |
| `cites_cross` | 跨包引用 `(package, seq, digest)` |
| `budget_consumed` | fuel、槽、字节 |
| `secret_slot` | 可选隐藏候选（承诺 + NIZK，见 6.1） |
| `digest` | 规范化字节的 SHA-256 |

转移规则 R（版本化）：同 home 父引用可达根、预算合法、verdict 只来自声明
检查器、只追加不覆盖；修正 = 新记录引用旧记录，绝不重写。

**字节边界（沿用 0155 第 6.1 节）**：摘要与后续签名/证明的输入必须是固定的
规范化字节（排序键、固定数字格式、固定字段顺序）。不得假定 Python 与 Rust
重新序列化同一 JSON 得到相同字节；实施时须先固定一种版本化规范编码。

## 5. L1：篡改可见脊梁

### 5.1 哈希链

```
H_0 = H(genesis)
H_i = H(H_{i-1} || package || seq_i || digest(R_i) || cites_cross)
```

定位能力：重算整链，第一个 `H'_i` 与记录值不同的位置即篡改点，其后全部
连带可疑。攻击者若连下游哈希一并重写，由锚点（5.3）兜底。

### 5.2 每包 Merkle 检查点

每包对其记录维护 Merkle 树；检查点文件（≤1 KiB）只含根、高度、记录数、
最后 seq、另两包检查点镜像。

### 5.3 全局锚点

`anchor.json` 含三包检查点、全局序号、锚点自哈希、Ed25519 维护者签名。
锚点自身成链：`anchor_{t+1} = H(anchor_t || 新检查点)`。锚点复制到
git tag、release 资产与三个包内嵌镜像。

### 5.4 根本信任边界（写入方案正文）

任何不攻破**全部**锚点副本的攻击都会被检查发现并定位；攻破全部锚点
（密钥失窃 + 所有镜像同步替换）是方案的信任边界。这不是一个可被“更长的
摘要”消除的问题，与 0155 第 2 节结论一致。

## 6. L2：零知识层

### 6.1 披露边界（L2a，无可信设置）

暂不公开的候选命题：记录只放 Pedersen 承诺 `C = g^{H(content)} · h^r`。

- Schnorr NIZK（Fiat-Shamir 变换，标准库可实现，对应
  `nizk_demo.py` 的 Demo 2）证明“我知道 (content, r) 能打开 C”，
  防止承诺跨记录挪用。
- 谓词 SNARK（复用 6.2 电路）证明“content 满足检查器 P 且与 C 绑定”。

披露时刻公布 (content, r)，此后任何人不需 ZKP 直接验证承诺。对应
Pascal 任务的披露边界语义：不披露不等于不存在，也不等于真。

### 6.2 谓词 SNARK（L2b）

把 R 与检查器判据算术化为电路，电路版本号进入记录。

| 方案 | 可信设置 | 证明大小 | 后量子 | 建议 |
| --- | --- | --- | --- | --- |
| Groth16（BN254/BLS12-381，即本地演示曲线） | 每电路需仪式 | 极小 | 否 | 需要时用，仪式文档化 + 毒废料销毁记录 |
| PLONK | 一次通用设置 | 小 | 否 | 多电路场景 |
| STARK | 无 | 大 | 是 | 研究库首选：透明设置最贴合“拒绝未认证来源” |

### 6.3 跨包包含证明（L2c）

引用他包记录时附 Merkle 包含路径，锚定被引包检查点；被引记录为秘密时
改用 6.1 的承诺 + NIZK。

### 6.4 可选 IVC（L2d，默认关闭）

`π_{i+1} = SNARK(π_i 有效 ∧ R(state_i, R_{i+1}) ∧ H_{i+1} 一致)`。末端
单个 π_n + 锚点即可 O(1) 验证全史。代价：证明者 O(n)、额外密码假设、
Groth16 需仪式。定位为纯加速：π_n 缺失或失败时回退 L1 全量重放；
**语义权威永远是 Rust 重放，SNARK 只是旁证**。

## 7. L3：检查协议与凭据工具

三个工具各管一段，互不替代：

| 工具 | 回答的问题 | 可用阶段 |
| --- | --- | --- |
| `key-issue` | 谁被授权发布哪类凭据（“谁”的签发） | Phase 0 |
| `verify` | 这一个凭据对象是否成立 | Phase 0（signature/inclusion）→ 1（disclosure）→ 3（ivc） |
| `tamper-check` | 整条发现序列与锚点是否一致 | Phase 0 |

### 7.1 tamper-check：整链完整性检查

新增 CLI，风格与 `math-check` 对齐：

```
python3 python/adva/adva.py tamper-check --root <任一包目录> \
    --anchor anchor.json [--zk] [--budget ...]
```

步骤：重算全部摘要（Python，与 `math-check` 同类完整性工作）；调用 Rust
后端重放转移规则（语义判定不交给 Python）；校验 Merkle 路径与锚点；
可选调用 `verify --kind ivc` 校验 π_n；报告。

| 报告状态 | 含义 | 退出码 |
| --- | --- | ---: |
| `Intact` | 全链与锚点一致 | 0 |
| `Tampered` | 首个分歧点 `(package, seq, expected, actual)` + 受影响区间 | 2 |
| `Unknown` | 预算耗尽、锚点缺失等，保留原因 | 3 |

纪律：只报告，绝不自动修复；修复 = 从完好副本恢复或追加更正记录，
走评审流程。

### 7.2 key-issue：密钥签发工具

**语义边界（先于任何命令）**。Pascal 任务词汇中 `key` 是“任务/呈现/见证
的引用坐标，既非认证也非解密密钥”。本工具的产物是密码学密钥材料，字段名
必须独立（如 `signing_pubkey_id`、`commitment_blind`），**不占用 `key`
一词**；任何 `key` 出现仍按原词汇解释。`secret` 的披露边界纪律同样适用：
不披露不等于不存在或为真。

本方案涉及的密钥/秘密材料只有三类，其余一律不引入：

| 材料 | 用途 | 生命周期 | 是否入链 |
| --- | --- | --- | --- |
| Ed25519 签名密钥对 | 锚点与签发记录签名（管“谁”） | 长期；轮换/撤销走签发记录 | 只公钥与 key-id 入链 |
| Pedersen 盲因子 r | 单个隐藏候选的承诺 | 一次性；披露时刻公布 | 否；只有承诺 C 入链 |
| SNARK 毒废料（Phase 2，若选仪式） | 生成证明/验证密钥 | 仪式后立即销毁，销毁记录入档 | 否；仪式记录摘要入链 |

盲因子不是“密钥”：本地随机生成即可，无需签发。key-issue 只管 Ed25519
签名密钥对的签发与授权绑定。

**命令与输入输出**：

```
python3 python/adva/adva.py key-issue --purpose anchor-signing \
    --home <条目 home> --version <策略版本> --validity <期限> \
    --output target/key-issue-record.json
```

- 私钥生成在离线/受控环境完成，熵源与生成过程记录进签发记录；
- 私钥**永不写入仓库、日志、命令行参数或候选可读空间**（0155 第 6.2 节）；
- 输出 `key-issue-record.json`：版本化 schema `adva.key-issue.record.v0`，
  含用途域、home、公钥标识、公钥字节、有效期、生成信息摘要、签发者签名；
- **签发记录本身作为一条 L0 记录追加进发现序列**，受哈希链与锚点覆盖：
  篡改签发记录与篡改发现记录一样可见。撤销 = 追加一条 `revoke` 记录，
  绝不删除原记录。

**授权边界（三谓词分离）**。签发只证明 `AuthorizedForPurpose`（该公钥依
独立策略有权用于此用途域），不推出 `SignatureValid`（待验）与
`SemanticallyChecked`（待 Rust 检查）。策略判定不交给工具自动完成：工具
只按固定策略文件执行格式与用途域检查，批准动作本身保留人工评审记录。
签发动作不授予任何数学权威或语义准入。

**拒绝控制与预算**：

| 控制 | 预期 |
| --- | --- |
| 未声明的用途域 | Blocked |
| home 或策略版本与固定清单不符 | Blocked |
| 私钥进入仓库/日志的路径尝试 | Blocked（检出即拒绝，不写任何文件） |
| 同一 key-id 二次签发（无轮换授权） | Blocked |
| 预算耗尽（子进程/文件写入上限） | Unknown，保留原因 |

### 7.3 verify：凭据验证工具

**与 tamper-check 的分工**。`tamper-check` 回答“整条链与锚点是否一致”；
`verify` 回答“**这一个**凭据对象是否成立”。tamper-check 内部可以调用
verify，但 verify 的判定不因链的完整性结论而改变，反之亦然。verify 的
Rejected 只表示该凭据对象不成立——**绝不表示被引命题为假**（对应
unknown_policy：拒绝一个候选不反驳解的存在）。

**命令与验证对象**：

```
python3 python/adva/adva.py verify --kind signature|disclosure|inclusion|ivc \
    --input <凭据文件> [--anchor anchor.json] [--budget ...]
```

| kind | 判定 | 需要的外部输入 |
| --- | --- | --- |
| `signature` | 精确消息字节在指定公钥下验签成立 | 公钥（来自受信渠道，非消息自述） |
| `disclosure` | C = g^{H(content)}·h^r，且 content 规范化摘要与链上记录一致 | 链上承诺记录 |
| `inclusion` | Merkle 路径在检查点根下包含成立 | 被引包检查点（锚点镜像） |
| `ivc` | π_n 通过 SNARK 验证 | 锚点 + 电路版本（Phase 3 起） |

每种 kind 报告 `Verified / Rejected / Unknown` 并附原因，与 Pascal 词汇
`verify` 的语义对齐（“检查声明的数学义务，报告 Verified、Rejected 或
Unknown 并附原因”）。退出码与 math-check 同风格：Verified → 0；
Rejected/Blocked → 2；Unknown → 3。每条报告保留输入摘要、判定、失败原因
（首个分歧点）、预算消耗与残余。

**字节与顺序纪律（沿用 0155 第 6.1 节）**。验证的输入必须是钉住的规范化
字节快照；禁止验签通过后重新读取可变文件而不再检查。公钥标识只是查找
坐标，不能代替从受信渠道得到的公钥。验证顺序（结构检查 → 范围检查 →
密码学检查）受预算约束，但密码学通过不能授权跳过结构、范围或后续的原生
语义检查。

**实现分工与拒绝控制**。验签、承诺验证、Merkle 路径验证是完整性计算，
Python 适配层可用已锁定的库执行；π_n 验证在 Phase 3 由 Rust 后端执行
（与 verifier-search 的监督模式一致）。畸形编码、截断输入、错误 kind、
未知电路版本 → Blocked；Python/Rust 对同一固定向量分歧 → 停止相关准入，
保留差异，不得投票（0155 第 8.1 节）。固定测试向量沿用 0155 第 8 节的
RFC 8032 / RFC 8439 选择纪律，正式验收前必须 pin 向量清单。

### 7.4 候选预算模板（非授权 run contract）

| 资源 | 候选上限 | 约束 |
| --- | ---: | --- |
| 单包记录数 | 100,000 | 执行前固定扫描清单 |
| 单记录字节 / 单文件 | 256 KiB / 8 MiB | 同 math-check 现有边界 |
| 总读取字节 | 64 MiB | 含锚点与镜像 |
| 总墙钟 | 5 秒（O(n) 重放）/ 另议（π_n） | 协作式期限，同 math-check 风格 |
| 重试 / 嵌套搜索 / 自动修复 | 0 / 0 / 0 | 失败保留；不重置 fuel |
| 原生准入 / 自动签署 | 0 / 0 | 本命令不产生准入或签名 |
| key-issue 单次签发 | 1 | 拒绝重试；签发记录写入计入总写入 |
| verify 单次调用凭据对象数 | 8 | 执行前固定清单 |
| 密码学后端操作（三工具共享） | 1,024 | 签名、验签、承诺验证及失败调用共享计数 |
| 生产密钥访问 | 0 | 研究校准只用公开测试材料；真实签发走受控环境 + 人工评审 |

## 8. 威胁模型

| 行为 | 需要的防护 | 单靠某层的不足 |
| --- | --- | --- |
| 修改记录但保留旧摘要 | 从锚点起复核字节 | 锚点被换后不能自救 |
| 修改记录并重算下游哈希 | 独立分发的锚点 + 计数/序号 | 锚点与内容同处一个可写目录则可被一起替换 |
| 拼接两条合法链 | 全局锚点 + 全局序号 | 包内哈希链不防分叉 |
| 跨包引用指向被改记录 | Merkle 包含证明 + 检查点镜像 | 被引包自身锚点失守后无法分辨 |
| 秘密候选在存储侧被盗 | 存储侧假设（另立文档） | ZKP 不防存储侧泄露 |
| 量子对手 | 摘要层按当前认知安全；SNARK 层仅 STARK 选项 | Groth16/PLONK 不提供 |
| 可信设置投毒 | STARK 规避；Groth16 靠仪式文档 | 电路再小也不能消除 |
| 正确签署了错误声明 | 原 Rust 语义检查 | 签名与 SNARK 都不纠正语义 |

## 9. 与现有机制的映射与边界

| 现有机制 | 本方案对应 |
| --- | --- |
| `stability` 加载器父链重放 | L1 哈希链把重放形式化并钉住 |
| `math-check` 只读校验 + 退出码 | `tamper-check` 同风格新增 |
| `index.json` 字节钉住 | 规范化序列化规则 |
| Research 0155（摘要/签名分离、字节边界、密钥生命周期） | L1 摘要 + 锚点签名；6.2/6.4 的仪式与密钥要求沿用 |
| `secret: payload_included: false` 披露边界 | L2a |
| Pascal 词汇 `key`（引用坐标，非认证/解密密钥） | 密码学材料用独立字段名，不占用 `key` |
| Pascal 词汇 `verify`（报告 Verified/Rejected/Unknown 附原因） | verify 工具报告语义与之对齐 |
| Research 0155 第 7 节三谓词分离 | key-issue 管 AuthorizedForPurpose；verify 管 SignatureValid；Rust 管 SemanticallyChecked |
| growth obligation Open、documentary seal ≠ 原生 Seal | 本方案只发 documentary 检查点，不声称颁发原生 Seal |

三种 seal 的区分沿用 0155 第 4 节：本方案的锚点与检查点属于 documentary
`seal` 一类；Ed25519 签名是第二类；Rust `WitnessProofV0::Seal` 是第三类，
本方案不接触。

## 10. 分阶段落地

| 阶段 | 内容 | 独立验收 |
| --- | --- | --- |
| Phase 0 | 规范化序列化、哈希链、Merkle 检查点、锚点镜像、`tamper-check`、`key-issue`（Ed25519）、`verify --kind signature/inclusion` | 改一字节→定位到 seq；锚点缺失→Unknown；伪造签名→Rejected；不做任何 ZKP |

Unknown、π_n 缺失降级重放、量子与仪式备注不并入验收结论。

## 11. 明确不做的事

- 不新增 Lisp 原生词；`tamper-check`、`key-issue`、`verify` 都是适配层命令。
- `key-issue` 不自动授权、不自动批准用途域；签发动作不授予语义准入。
- `verify` 的 Rejected 只表示凭据对象不成立，不表示被引命题为假。
- 不发原生 `Seal`、不自动重封、不自动修复、不重写历史。
- ZKP 不替代 Rust 语义重放；SNARK 有效性仅等于其电路对检查器的忠实度。
- 公开记录不承诺机密性；ZKP 只覆盖声明的 `secret_slot`。
- 不把本方案描述为“不可篡改的账本”，只承诺“篡改可见、可定位”，
  且以锚点未全面失守为前提。

## 14. 六方合并的次序安排（排序分数条目）

状态：设计登记（2026-09-07），不是已执行的 merge 证据，不改变第 12 节
开放问题的未决状态。

### 14.1 适用范围

两侧（Python 传输侧 / Rust 原生侧）数值一致前提下的六方合并过程：合并以
两两步骤进行，本条目只规定**合并步骤的次序**，不规定参与方的资格（资格
由 key-issue 用途域与 Rust 语义判定固定）。

### 14.2 排序分数定义

- **合并残差**：对任意合法候选对 (a, b)，`r(a, b) = |norm(v_a) − norm(v_b)|`，
  其中 `norm` 把两侧数值归一化到同一精确表示后再比较（f64 与精确有理的
  同值情形归一化后残差为 0）；
- **排序规则**：min-residual-first——每步在所有合法候选对中选残差最小者
  合并；候选对合法当且仅当双方均未被合并且满足既定 admission 条件；
- **决胜规则（tie-break）**：残差相等时按 party 序号字典序取最小对；
  party 序号由 key-issue 用途域注册顺序确定，固定且可重放；
- **确定性**：以上规则不含随机性；给定相同的参与方集合与数值，合并次序
  唯一确定。

### 14.3 纪律边界

- **分数只排序、不录取**：admission 与语义判定不因次序改变；任何合法
  次序的合并结果（值一致断言）相同，次序只影响证据路径与效率；
- 分数与次序以 documentary 字段（`order_score`、`order_rank`）记入每条
  merge 记录，不进入哈希链的语义层、不替代六方签名认证；
- **全残差为零时 tie-break 接管**——这是两侧同值（当前 14.0 场景）的常态，
  次序退化为 party 序号递增的固定序列；
- 排序不佳不产生语义错误，仅可能增加证据路径长度。

### 14.4 工作示例（当前场景）

- 两侧数值均 14.0 → 所有合法对残差为 0 → tie-break 按 party 序号定序；
- 一侧为 f64 14.0、另一侧为精确有理 14 → 归一化后残差仍为 0；
- 若某侧数值被篡改为 15 → 含该侧的对残差为 1，被排到最后，且其合并的
  值一致断言为 Rejected（残差保留）。

### 14.5 机制先例与域边界

- 机制先例：Research 0152 的残差引导（residual-guided）搜索；
  Research 0129 明文"分数可以给可接受提案排序，但不推翻录取"；
- 域边界：本条目**不借用** LABS 的 energy/merit 数值（跨域翻译未证成，
  0129 第 3 节禁止），只借用"分数排序"这一机制本身。
